# Клуб «Лунный камень» — онлайн-казино на Python

Рабочее казино на Flask: три игры, учётные записи, журнал ставок и
математически проверяемая честность. Фишки виртуальные.

Проверено на Python 3.12. Единственная внешняя зависимость — Flask;
база, криптография и хэширование паролей взяты из стандартной библиотеки.

---

## Шаг 1. Установка и запуск

```bash
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install flask
python3 app.py
```

Откройте `http://127.0.0.1:5000`, нажмите «Открыть счёт» — новый игрок
получает 1000 фишек. База `casino.db` создаётся сама при первом запуске.

## Шаг 2. Из чего состоит проект

| Файл | Ответственность |
|---|---|
| `games.py` | Генератор случайности и правила трёх игр. Денег не касается. |
| `db.py` | SQLite: пользователи, балансы, журнал ставок, пароли. |
| `app.py` | HTTP: маршруты, сессии, валидация, расчёт выплат. |
| `verify.py` | Отдельный скрипт: проверка честности прошлой ставки. |
| `templates/`, `static/` | Интерфейс: две страницы, один CSS, один JS. |

Разделение не декоративное: `games.py` не знает про баланс, поэтому его
можно тестировать и пересчитывать миллионами итераций без базы.

## Шаг 3. Как устроена честность (provably fair)

Исход ставки определён **до** её совершения тройкой значений:

1. `server_seed` — 32 случайных байта, сервер хранит их в секрете;
2. `client_seed` — строка, которую задаёт игрок;
3. `nonce` — порядковый номер ставки, растёт на единицу после каждой.

```
HMAC-SHA256(ключ = server_seed, сообщение = "client_seed:nonce:cursor")
    → 32 байта → по 4 байта на число → число / 2³² → [0, 1)
```

Игрок заранее видит `SHA-256(server_seed)`. Сервер не может подкрутить
результат задним числом: любое изменение сида ломает опубликованный хэш.
Нажатие «Раскрыть серверный сид» показывает старый сид и выдаёт новый.

Проверка вручную:

```bash
python3 verify.py <server_seed> <client_seed> 0 dice
```

Скрипт печатает SHA-256 сида и пересчитывает исход. Хэш обязан совпасть с
тем, что вы видели до игры, а исход — с тем, что показало казино.

## Шаг 4. Математика игр

Казино зарабатывает на разнице между честным и выплачиваемым коэффициентом.

**Кости.** Ставка «выпадет меньше X». Шанс = X/100, честная выплата = 100/X.
Платим `(100/X) · 0,99` — преимущество заведения ровно 1% при любом X.

**Рулетка.** 37 секторов, выплаты честные для 36 чисел. Всё преимущество
даёт зеро: 1/37 = 2,70%. Отдельный срез коэффициента не нужен.

**Слоты.** RTP задаётся таблицей выплат и весами символов:

```
RTP = Σ p³·выплата_за_три + Σ 3p²(1−p)·выплата_за_пару
```

Функция `games.slots_rtp()` считает это точно, без симуляции. Текущая
настройка даёт **95,9%**. Меняя таблицу, обязательно запускайте её:

```bash
python3 -c "import games; print(games.slots_rtp())"
```

Первая версия этой таблицы выдавала RTP 209% — заведение теряло бы по
фишке на каждую поставленную. Такие ошибки на глаз не видны.

## Шаг 5. Где проект защищён и почему именно там

**Клиенту не верят ни в чём.** Браузер присылает только намерение: игра,
сумма, параметры. Исход, коэффициент, выплату и баланс считает сервер.
Подделать POST-запрос легко — поэтому в нём нет ничего ценного.

**Деньги в целых числах.** Баланс хранится в сотых долях фишки как `INTEGER`.
`0.1 + 0.2 != 0.3` для float, и на миллионе ставок это превращается в
расхождение кассы.

**Одна транзакция на всю ставку.** Проверка баланса, списание, начисление и
запись в журнал идут внутри `BEGIN IMMEDIATE`. Без этого два одновременных
запроса потратят один и тот же баланс дважды — классическая атака на казино.
Тест: 20 параллельных ставок при балансе ровно на одну — проходит одна,
баланс останавливается на нуле.

**Пароли через scrypt** с индивидуальной солью, сравнение постоянного времени.
Форма входа не уточняет, логин неверен или пароль, — иначе она становится
инструментом для перебора существующих аккаунтов.

**Cookie сессии** помечена `HttpOnly` и `SameSite=Lax`.

## Шаг 6. Как добавить свою игру

1. В `games.py` напишите функцию, принимающую список чисел `[0,1)`
   и возвращающую `{"win", "multiplier", "text", ...}`.
2. Укажите в `ROLLS_NEEDED`, сколько чисел нужно — это фиксирует порядок
   их расходования, иначе проверка честности перестанет быть однозначной.
3. Добавьте ветку в `play()`.
4. Посчитайте RTP формулой или симуляцией **до** публикации.
5. Добавьте вкладку в `index.html` и отрисовку в `renderStage()`.

## Шаг 7. Чего здесь нет — и что это значит

Этого достаточно для учебного проекта, портфолио или игры с виртуальными
фишками среди друзей. Для приёма реальных денег потребуется:

- **лицензия** регулятора (Мальта, Кюрасао, Гибралтар и др.) — без неё приём
  ставок на деньги является уголовным преступлением в большинстве стран;
- **KYC и AML**: проверка личности, мониторинг подозрительных операций;
- **сертификация ГСЧ** независимой лабораторией (eCOGRA, GLI, iTech Labs);
- **инструменты ответственной игры**: лимиты депозита, самоисключение,
  пауза по запросу, видимая статистика проигрышей;
- **боевая инфраструктура**: PostgreSQL вместо SQLite, gunicorn за nginx,
  HTTPS, CSRF-токены на формах, ограничение частоты запросов,
  неизменяемый аудит-лог ставок, `SECRET_KEY` из переменной окружения.

Платёжный провайдер не подключится к проекту без первых двух пунктов, так
что начинать нужно с лицензии, а не с кода.
